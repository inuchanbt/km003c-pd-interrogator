# 純正2.0.7への別置き拡張 — 接続試作と更新・復旧検証

[English](OVERLAY-207.md) · 日本語

対象は既知ハッシュのHW2.3／純正2.0.7だけです。
接続試作の書込み・起動・完全復元を実機確認し、QR画面、PDO保持、追加GETへ拡張しました。
対象loaderに限定する更新ツールは [native-host/README.md](../native-host/README.ja.md)、
実機結果は [HARDWARE-2026-11-05.md](HARDWARE-2026-11-05.ja.md) に記録しています。

## 配置

| 領域 | 配置と用途 |
| --- | --- |
| 純正アプリ | `0x4000..0x738bf`。既存命令の変更はGUI入口8バイトとループ4バイト |
| 判定処理 | `0x738c0` から264バイト（Clang 23.1.4）。通常アプリ末尾の余白内 |
| 拡張ヘッダー／コード | `0x74000` から9,672バイト（追加GET・完了結果保持・実測QR）。先頭64バイトにABI・長さ・CRC・関数ポインター・純正ハッシュ |
| 拡張上限 | リンカーは `0x7c000` 未満に制限。専用更新profileは `0x78000` までの2追加セクターに限定 |
| SRAM | この接続試作の静的な可変領域は0バイト。新しい固定RAMアドレスを予約しない |

純正バックアップの `0x738c0..0x7ffff` は消去状態でした。
この観測だけで、純正が将来の操作でも使わないと証明したことにはなりません。
今回の試験前にも通常／DFUで全領域を再読取し、試作の起動後にも一致を確認しました。
QRと追加GETの確認範囲は [NATIVE-INFO-207.md](NATIVE-INFO-207.ja.md) を参照してください。
フラッシュへの測定保存は含みません。
ブートローダー・ICG・OTP校正・外部NORは変更対象に含めません。

## 起動とフォールバック

1. GUIタスク入口で、純正末尾側の判定処理へ分岐する。
2. 拡張のmagic、ABI、サイズ、純正ビルドのハッシュ識別子、Thumb入口、全体CRC32を確認する。
3. 正常なら拡張のGUIコールバック、不正／未配置なら純正GUI handlerをR8に保持する。
4. 置換した純正の2命令を再実行し、元の初期化処理 `0x1ebb8` に戻る。
5. GUIループはR8のコールバックを呼び、その後の純正の待ち・処理を継続する。

対象のGUIタスクはこの範囲でR8を使用せず、呼び出される関数はAAPCSの保存規約に従います。
純正PendSVでは `0x438a` でR4〜R11を保存し、`0x43a8` で復元しています。
このため、コールバック用に固定RAMや純正の非公開構造体の空き領域を使わずに済みます。
GUIタスクの再生成時は再検証されます。CRCの検証は毎フレームではなく入口で一度だけです。

現時点の拡張GUIコールバックは、元のhandlerを1回呼ぶだけです。
QR APIに加え、純正画像オブジェクトと入力グループで動くQRデモを追加しました。
純正ヒープから作業領域・1ビット画像を借り、Exitで解放します。
固定RAM・追加のタスク保存レジスターは使用しません。詳細は [NATIVE-GUI-207.md](NATIVE-GUI-207.ja.md)。
現在は、本体が所有するPDOのコピーから同じQRを生成します。結果の固定とIDの条件は
[NATIVE-CAPTURE-207.md](NATIVE-CAPTURE-207.ja.md) に分けています。
CRCは破損検出です。判定処理自体や純正部分の破損からの復旧を保証するものではありません。

## オフライン検証

通常の56件のテストに加え、次を実行します。Unicorn 2.1.4、Node.js、Clang/LLDが必要です。

```powershell
python tools/build_overlay207.py --clang C:\path\to\clang.exe
python tools/check_overlay207.py artifacts/overlay207
python tools/check_native_arm.py artifacts/overlay207/overlay207-offline.elf --overlay
```

- 配置をリンカーで制約し、可変data/bssがあればビルド失敗にする。
- 正常、欠落、ヘッダー各語と本体の破損、不正な長さ・入口の28ケースで、ARM命令を実行する。
- GUI入口への復帰、タスク引数・スタック・保存レジスター、各ケース3回の純正handler呼出しを確認する。
- 別置きコードのKPD1生成・URL・全5枚のRGB565画像を、Python版とスマホ用jsQRで確認する。

純正GUI handlerは呼び出し回数確認用スタブに置換して検証しています。
実際のGUI初期化、割り込みとの同時動作、PD/EPRの時間制約、液晶表示はこの検証に含みません。
28ケースは56件のPythonテストとは別のARM検証です。

## この個体のブートローダー

バックアップのloader SHA-256:

```text
8e972bbd2abffa199d465082f473823372e32d4b4c86574664a976afd2797809
```

HW2.1の既存資料と同じ実装ではありません。`tools/inspect_loader23.py` で、このハッシュだけを
対象に、純正scatter-loadと消去／書込み関数、通常のアプリ分岐経路をPC上で調べました。
Capstone 5.0.7も別途必要です。

```powershell
python tools/inspect_loader23.py C:\private\loader-00000004-00003fff.bin
```

この個体の通常分岐 `0x20c8` では、retention値とSP範囲を確認してreset vectorを呼びます。
この経路でcommitted sizeの参照はなく、モデル上でも拡張サイズで分岐しました。
消去関数は提案範囲 `0x4000..0x74ff4` を受け付け、最後のセクター開始は `0x74000` でした。
書込み関数もモデル上で追加領域へ32バイトを書けました。
範囲、フラッシュready、cacheの簡略モデルであり、実機の書き込み成功を示すものではありません。
USB転送、暗号処理、完了判定、電源断、フラッシュの実際の時間は検証していません。

## 非公開候補と復旧計画

対象個体のバックアップを既存backupツールで `verify --require-dfu` した上で、候補を作れます。

```powershell
python tools/prepare_overlay207.py --stock C:\private\qualified-stock-backup
```

これはUSBを開かず、パッケージ暗号化や更新プロトコルも扱いません。
原本とmanifestの照合、純正／loaderの既知ハッシュ、末尾の重複範囲、追加先の消去状態を確認します。
純正バイナリを含む候補と展開後コードは `artifacts/` 内の新規フォルダーにだけ出力し、公開しません。
既存命令の変更は2箇所12バイトで、サイズ／CRCの8バイトを未コミット状態へ戻します。

通常のkm003c-libは `0x6fffe` の上限でこの候補を拒否します。
固定版へのローカルfeature `hw23-overlay` と専用ホストを追加しました。
**このloaderハッシュとHW2.3、既知の純正prefixを確認した場合だけ**拡張範囲を許可し、
2追加セクター、最小AES余白、既定の2箇所の命令変更に限定します。
通常の上限と既存の認証・転送処理は維持しています。
実機でも、書込み前後と起動後に全内部領域・loader・隣接領域を照合しました。

元の純正restoreだけでは `0x74000..0x77fff` の拡張セクターが残ります。
完全に原状へ戻すには、DFUのまま、拡張まで消去する純正のパディング付きerase passを通して照合し、
その後に元のqualified restore containerを適用して、本来のサイズ／CRCと全バイトを戻す計画です。
1追加セクター版では、2段階とも読み戻しとloader不変を実機確認し、純正の再起動後にも内部全体の一致を確認しました。
2追加セクター版では全内部領域に対する復元モデルまで確認済みで、実際の復元書込みは未実施です。
最後に校正領域1024バイトを照合し、利用者が純正画面とボタン操作への復帰を確認しました。
